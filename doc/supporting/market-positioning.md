# 市场定位与真实价值

## 一句话定位

MarketMind Agent 是一个面向电商运营场景的工程化 Agent 系统，重点解决评论洞察、证据链报告和长任务可追踪，而不是替代成熟卖家工具。

更准确的中文副标题：

> 电商评论洞察与证据链报告 Agent

## 为什么不是“大而全卖家工具”

成熟卖家工具通常覆盖关键词、销量估算、广告、排名、库存、利润、竞品监控等大量能力。第一版项目不应该和这些工具正面竞争。

本项目不做：

- 不做全平台商品库
- 不做销量和 GMV 估算
- 不做关键词投放建议
- 不做广告和库存管理
- 不做全网稳定爬虫
- 不承诺替代 Helium 10、Jungle Scout、卖家精灵等成熟工具

本项目要做的是一个更窄、更可解释、更适合工程展示的切面：

- 从评论中提取用户痛点
- 从差评中定位产品缺陷
- 从证据片段生成可追溯报告
- 把长任务状态、Agent step、失败原因全部落库

## 目标用户

第一版主要服务三类用户：

| 用户 | 真实痛点 | 本项目提供什么 |
| --- | --- | --- |
| 电商运营 | 手动翻评论慢，痛点总结零散 | 自动聚类差评、提取痛点、生成报告 |
| 选品/产品分析人员 | 判断机会点缺少证据 | 报告结论关联原始评论和评分 |
| 学生/开发者 | Agent 项目容易变成薄 demo | 展示异步任务、状态机、RAG、pgvector、前后端联调 |

## 真实价值边界

### 对业务用户的价值

- 节省人工翻评论时间
- 快速看清质量、物流、售后、包装、价格等问题集中在哪
- 让报告结论可以回溯到原始评论
- 在真实网页采集失败时，仍可用 CSV/JSON 数据走完整分析链路

### 对工程项目的价值

- 证明长任务不是用 HTTP 请求硬扛，而是通过 Celery 解耦
- 证明 Agent 不是黑盒，而是 Thought / Action / Observation 可追踪
- 证明 RAG 不是只“向量化一下”，而是能支撑报告证据链
- 证明系统具备失败记录、重试、回退和可观测能力

## 核心差异点

普通 AI 总结工具的问题：

- 把评论一次性塞给模型，容易超上下文
- 总结结论没有证据来源
- 中途失败后难以恢复
- 无法复盘模型为什么这么判断

MarketMind Agent 的差异：

- 评论清洗、切片、embedding、pgvector 检索
- 报告中的关键结论引用 `review_chunk_id`、评分、来源 URL
- 任务状态、Agent step、工具输入输出全部持久化
- API 提交后立即返回 `task_id`，长任务由 worker 异步执行

## 市场必要性判断

这个方向有需求，但必须收窄。

需求成立的原因：

- 电商运营确实需要分析大量评论
- 竞品差评能反映用户痛点和产品机会
- 运营报告需要可解释证据，而不是一句模型总结
- 长任务和多步骤分析需要工程化系统承载

需要警惕的地方：

- 成熟卖家工具已经很多，不能讲成“全功能替代”
- 真实站点采集不稳定，必须有 Demo Dataset 和 CSV/JSON 兜底
- 小卖家未必愿意为单点工具付费，第一阶段更适合内部工具或简历项目
- 没有真实数据统计前，不要夸大节省时间和分析准确率

## 产品边界

第一版产品边界：

- 输入：URL、Demo Dataset、CSV/JSON 评论数据
- 处理：采集、清洗、切片、embedding、语义检索、Agent 分析
- 输出：带证据引用的评论洞察报告
- 观测：任务状态、Agent steps、错误分类、token 成本

不在第一版：

- 多用户权限系统
- 复杂代理池
- 全站点采集适配
- 广告投放建议
- 销量预测
- 自动下单或自动运营

## 简历口径

推荐写法：

> 设计并实现面向电商运营的评论洞察 Agent 系统，基于 FastAPI、Celery、Redis、PostgreSQL/pgvector、Playwright 和 Next.js 构建异步采集、评论 RAG 检索、Agent 状态持久化和带证据链的报告生成闭环。

不要写：

> 替代成熟电商卖家工具的 AI 选品平台。

原因是后者范围过大，且容易被质疑数据来源、销量估算和商业可行性。
