# 面试讲述稿

## 推荐讲法

先讲问题：人工翻竞品评论很慢，普通 AI 总结缺少证据链，长任务容易中断，信息难复用。

再讲方案：用 FastAPI 接任务，Celery 异步执行，Playwright 采集，Agent 做决策，PostgreSQL 存状态，pgvector 做检索。

最后讲结果：系统可以追踪每一步，支持恢复，能生成结构化报告。

## 2 分钟版本

这个项目解决的是电商运营里“评论太多、痛点难归纳、报告缺证据”的问题。用户提交商品链接或评论 CSV/JSON 后，FastAPI 创建任务并交给 Celery，Worker 后台调用 Agent。Agent 不直接一次性生成报告，而是按 ReAct 流程调用采集、评论检索和报告工具。每一步 Thought、Action、Observation 都写入 PostgreSQL，所以失败后能定位和恢复。评论数据会清洗、切片、向量化进 pgvector，报告生成时通过语义检索找出质量、物流、售后等问题证据，最后输出带引用的评论洞察报告。

## 市场定位怎么讲

这个项目不是要替代成熟卖家工具。成熟工具覆盖关键词、销量估算、广告和库存，本项目第一版聚焦一个更窄的高价值切面：评论洞察、差评证据和长任务可追踪。

这样讲更稳：需求是真实的，因为运营确实需要快速理解大量评论；范围也是克制的，因为系统不承诺全网稳定采集和销量预测。

## 可能被追问的问题

### 为什么不用一个脚本直接跑

因为真实任务会持续数分钟，HTTP 请求容易超时，而且失败后很难恢复。用 FastAPI + Celery 可以把任务提交和任务执行分开，用户体验和系统稳定性都更好。

### 为什么 Agent 状态要落库

因为长任务中模型、爬虫、网络都可能失败。如果只靠内存，一旦中断就只能重跑。落库后可以从最后成功的 Observation 继续。

### RAG 在这个项目里解决什么

评论数量一多，不能直接塞给模型。RAG 把评论切片向量化，Agent 查询某个问题时只召回相关片段，既省 token，也让报告有证据。

### 爬虫被拦怎么办

第一版不做违法绕过。系统会做限速、等待、失败截图和错误分类，并支持 CSV / JSON 手工导入，保证主链路不被单一站点卡死。

### 如何证明不是玩具项目

不是只展示页面，而是展示任务队列、状态表、Agent step、失败重试、向量检索结果、报告证据链和 GitHub 提交历史。
